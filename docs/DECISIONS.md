# 工程决策记录

| 决策 | 备选方案 | 为什么选它 | 代价 | 边界/不适用场景 |
|---|---|---|---|---|
| 生产模块迁入 `app/`，根目录保留兼容 shim | 一次性删除根模块并重写所有脚本 | 先降低迁移风险，保证现有 URL、CLI 和 import 不中断 | 根目录会暂时保留薄兼容文件 | P1-B 完成调用方迁移后应继续收敛 |
| 使用标准库 JSON 结构化日志 | 引入 structlog/ELK，或继续 print | 当前没有日志平台，标准库足以形成可解析基线 | 暂时只能输出到 stdout，没有集中查询 | 多实例生产环境后续应接入日志平台 |
| 使用 `ContextVar` 传播 request_id | 每个函数显式传 request_id | API、数据同步和 LLM 日志可自动串联 | 异步任务若脱离请求上下文需重新绑定 | 后台任务必须显式设置上下文 |
| 数据文件未变化时先比较元数据，不重新解析全文件 | 每次查询都读取完整 CSV/JSON | 避免小数据测试掩盖大文件性能问题 | 首次使用旧库时可能触发一次全量同步 | 文件哈希本身仍需读取字节流，大规模文件应进一步优化 |
| 启动时数据初始化失败直接终止 | 捕获后继续启动，等首个请求再报错 | 防止“服务看似可用但数据不可用”的假健康状态 | 错误会阻断启动，需要运维查看结构化日志 | 若未来要求降级运行，应显式提供只读/缓存模式 |
| 错误响应同时保留 `detail` 并增加 `error` | 立即只返回新 envelope | 保持现有客户端兼容 | 响应暂时存在字段重复 | P3 版本化 API 时再决定是否移除旧字段 |
| 覆盖率门禁用标准库 `trace` | 安装 coverage.py/pytest-cov | 当前网络不可用，项目仍需要可执行门禁 | 只统计行覆盖，不提供分支覆盖 | 网络可用后可在 P6 替换为 coverage.py |
| 生产/测试/开发依赖分文件 | 所有包放进同一个 requirements | Docker 只装生产依赖，CI 不安装大型向量运行时 | 需要维护三个清单 | 若采用统一镜像构建，可合并为约束文件 |
| 学习稿移到 `scripts/learn/`，运维工具移到 `scripts/tools/` | 保持根目录平铺 | 生产入口与学习代码边界清晰 | 部分命令改为 `python -m scripts...` | 根目录 `main.py` 兼容入口暂时保留 |
| Docker 默认运行完整生产依赖 | 只做 CPU/无 AI 镜像 | `/diagnose` 在镜像内可直接工作 | 镜像包含 torch，体积较大 | 若部署环境不需要 LLM，可另建轻量镜像 |
| 数据文件无效时服务保留运行并阻止业务查询 | 启动直接失败，或回退使用旧数据库 | 质量接口仍可返回明确原因，同时避免旧数据被当成当前结果 | 运维必须查看健康检查和质量接口 | 若部署策略要求 fail-fast，可切换启动模式 |
| 脏数据按整行拒绝，不做自动填充 | 插值、填默认值、只跳过错误字段 | 避免无依据的工艺数据进入评分和 AI 上下文 | 有效记录数量可能下降 | 真实系统应结合工艺规则和数据补齐流程 |
| 阈值使用 JSON 规则文件并支持设备覆盖 | 继续只使用环境变量 | 规则可评审、可版本化，支持类型和单设备差异 | 规则文件需要校验与测试 | 工艺变化频繁时仍需要配置发布流程 |
| 为生产批次增加可空 `production_time` | 使用导入时间伪装成生产时间 | 保持语义正确，并支持真正的时间范围过滤 | 旧文件缺少时间时不会命中时间过滤 | 真实系统应从 MES/采集时间字段映射 |
| 旧数据库使用 `ALTER TABLE` 增量迁移 | 删除重建数据库 | 保留历史记录并满足兼容要求 | 迁移逻辑需要长期维护 | 复杂 schema 变化应使用版本化迁移工具 |
| 排序字段使用固定白名单 | 动态拼接客户端列名 | 防止 SQL 注入和无效列访问 | 新字段需要同步维护白名单 | 大范围自定义分析应使用受控查询层 |
| 新记录接口使用 `data/meta` envelope，旧接口保持不变 | 立即包装所有旧接口 | 新接口结构统一且不破坏既有客户端 | 响应风格暂时双轨 | API 大版本升级时统一迁移 |
| RAG 使用语义段落切分而非固定滑窗 | 纯固定字符切分 | 保留标题、规则和参数边界，同时保留长度上限与重叠 | 切分逻辑比固定窗口复杂 | 无结构的超长扫描件仍需专用解析 |
| 索引落盘为 JSON + NPY + manifest | 每次进程内重建，或引入向量数据库 | 当前 3 文档规模无需外部服务，同时支持哈希增量刷新 | 只适合中小知识库，无 ANN 索引 | 大规模并发知识库应换专用向量索引 |
| 向量检索与 BM25 混合 | 纯向量或纯关键词 | 兼顾语义表达和半导体术语精确匹配 | 需要维护两路分数和阈值 | 权重必须用评估集回归，不应凭感觉调整 |
| 无词法证据时提高语义阈值 | 所有查询固定返回 top-k | 避免无关问题被强行召回 | 可能过滤部分弱语义关系问题 | 需要持续维护负例问题集 |
| 30 条固定评估集与负例门禁 | 只做人工看几个检索结果 | 检索改动可重复度量并防止指标回退 | 数据集本身也需要防止过拟合 | 后续应扩展真实脱敏文档和多答案标注 |
| LLM 使用 Pydantic 模型生成 JSON Schema | 只写自然语言格式要求 | 模型、Prompt 和运行时使用同一输出契约 | 修改字段需要同步模板和测试 | 复杂跨字段约束仍需手写业务校验 |
| 非法输出只自动修复一次后降级 | 无限重试，或直接返回错误 | 控制延迟和成本，同时保证接口可用 | 某些可在第二次修复的输出会失去 LLM 形态 | 高价值离线任务可使用更长的异步重试链 |
| 评分和风险由规则锁定，LLM 不得修改 | 让模型自行复核数值 | 避免模型计算漂移和事实污染 | 报告表达能力受事实结构限制 | 人工调整必须走规则配置而不是 Prompt |
| LLM 调用统计持久化到 SQLite | 仅存内存 | 服务重启后仍能查看调用成功率与延迟 | 每次调用多一次小事务 | 高并发多实例应使用集中指标系统 |
| CI RAG 回归使用确定性 Embedding | CI 下载完整语义模型 | 保证每次推送都能快速执行 30 条检索门禁 | 不验证真实模型权重变化 | 发布前仍执行真实语义模型评估 |
| 固定数据使用 JSON 回归快照 | 只断言局部字段 | 规则变化会明确暴露整体结论变化 | 合法规则调整需要更新快照 | 快照必须附带变化原因 |
| 覆盖率暂时使用标准库 trace | 等待 coverage.py 可用 | 当前无网络也能执行 80% 核心门禁 | 分支覆盖和线程内 FastAPI 行不完整 | 网络恢复后应在 P6/P7 升级 coverage.py |
| 阈值优先级为「环境变量 > JSON 规则文件 > settings 默认值」 | 环境变量无条件覆盖 | JSON 是可评审、可版本化的规则来源；环境变量只在显式配置时代表临时覆盖 | 未设置变量时行为依赖 JSON，配置错误会直接生效 | 多环境部署应通过 `.env` 或编排层显式注入，不要依赖代码内默认值 |
| `GET /diagnose` 只读、`POST /diagnose` 落库 | 保留 GET 写历史，或加 `persist` 查询参数 | GET 必须幂等，刷新页面不应产生新的诊断记录；写操作走 POST 语义正确 | 需要调用方区分两个方法，OpenAPI 中多一个端点 | 若前端只做预览，应使用 GET 并自行决定何时 POST |
| 诊断检索按 `equipment_type ∈ {当前设备, general}` 过滤，无命中再放宽 | 全部不做过滤，或严格只取同设备 | 设备专属知识优先，同时保留对任何设备都成立的通用规则；空结果时才降级，避免上下文为空 | 放宽时相关性下降，需要 `filters_relaxed` 字段暴露 | 知识库按设备拆分粒度不足时，过滤收益有限 |
| 索引新鲜度用 mtime+size 签名，热路径不算哈希 | 每次查询重算全库 SHA-256 | 每次检索只做一次 stat，把哈希留给构建期；编辑、checkout、覆盖写入都能被签名捕获 | 同尺寸且 mtime 被刻意保留的修改可能漏检 | 高完整性场景应提供 `verify` 强制按哈希校验 |
| `POST /diagnose` 的 `persisted` 反映实际写入结果 | 直接回显请求里的 `persist` 开关 | 去重或校验拦截时并没有新增记录，字段若仍为 true 会误导调用方与看板统计 | `save_diagnosis` 需要返回布尔值，调用方要区分“请求落库”和“确实落库” | 只关心是否调用过写接口的场景，需要另看 `diagnosis_saved` / `diagnosis_deduplicated` 日志 |
