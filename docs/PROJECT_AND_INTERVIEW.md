# 项目说明、半导体业务映射与面试表达

## 1. 项目一句话介绍

这是一个使用模拟生产数据构建的半导体设备生产分析与异常识别演示项目：
后端读取外部 CSV/JSON，将数据同步到 SQLite，通过规则识别温度、压力和
良率异常，计算健康评分与历史趋势，并通过 FastAPI、仪表盘和 JSON API
提供查询能力。

> 所有生产数据均为模拟数据。项目没有接入真实晶圆厂 MES、设备网络或
> 真实工艺配方，不能表述为真实工厂生产经验。

## 2. 系统架构

```text
data/production_data.csv 或指定 JSON
                |
                v
      production_source.py
      读取、字段映射、数据校验
                |
                v
      database_manager.py
      内容哈希检测 + SQLite 同步
                |
                v
       database_query.py
      设备、批次、异常相关 SQL
                |
                v
       anomaly_analysis.py
      温度/压力/良率规则 + 统计
                |
                v
 health_score.py / trend_analysis.py
      评分、风险等级、趋势
                |
                v
      main_api.py
 JSON API + HTML 仪表盘
```

数据库表：

```text
wafer_production
  id, batch_id, equipment_id, process,
  temperature_c, pressure_kpa, yield_pct

data_source_meta
  source_path, signature, record_count, synced_at
```

## 3. 关键设计决定

### 外部文件是数据源，SQLite 是查询缓存

真实工业系统通常由 MES、设备采集系统或数据平台提供数据。当前项目用
CSV/JSON 模拟这一层，避免把模拟数据写死在 Python 代码中。

应用记录文件内容哈希。文件内容变化时，在同一事务中替换生产记录，因此
不会把旧数据和新数据混在一起。

### 异常统计和健康评分共用同一份结构化结果

`build_equipment_analysis()` 一次查询同时产生：

- 异常事件列表；
- 异常类型计数；
- 涉及异常批次数；
- 正常批次数；
- 平均温度、压力和良率。

健康评分直接使用这份异常事件列表，避免页面统计和评分各算一套。

### 页面只负责展示，不调用大模型

仪表盘是确定性数据看板，打开页面不依赖 DeepSeek 或向量模型。大模型
诊断报告保留在 `/diagnose/{equipment_id}`，属于后续 RAG 阶段。

## 4. 演示阈值与统计口径

| 规则 | 演示阈值 | 评分扣分 |
|---|---:|---:|
| 温度异常 | `temperature_c > 100` | 15 |
| 压力异常 | `pressure_kpa > 120` | 10 |
| 低良率异常 | `yield_pct < 90` | 30 |

这些数值仅用于演示，不是半导体行业统一标准。

统计口径：

- 异常事件数：同一批次触发两个规则，记两条事件。
- 异常批次数：同一批次无论触发几个规则，只算一个批次。
- 正常批次数：生产批次数减去异常批次数。

## 8. 面试讲述顺序

建议按“问题 -> 方案 -> 证据 -> 边界”讲：

1. 问题：想模拟半导体设备数据看板和异常分析，但初始代码把设备编号和
   模拟数据写死在逻辑中。
2. 方案：改成外部文件数据源，增加校验和 SQLite 同步，统一异常统计、
   评分和趋势规则。
3. 证据：3 台设备、30 个批次、异常事件与评分一致，自动化测试通过，
   API 和仪表盘都能按设备切换。
4. 边界：没有真实 MES 接入、没有真实传感器数据、没有真实产线验证，
   所有规则和结果均为演示。

## 9. 常见面试问题

### 为什么不用直接把 CSV 读到内存？

小数据可以，但项目需要模拟工业系统中的持久查询和 SQL 分析。SQLite
适合演示设备、批次和汇总查询；外部文件仍是可替换的数据入口。

### 如何保证文件更新不会产生半套数据？

删除旧记录、写入新记录和更新同步元数据在同一数据库事务中完成。失败时
回滚，读取方不会看到只导入一半的数据。

### 为什么异常事件数和异常批次数不同？

一个批次可能同时有温度、压力和良率问题。事件按规则命中计数，批次按
`batch_id` 去重计数，两者回答的是不同业务问题。

### 为什么趋势图按生产批次累计扣分？

诊断记录只有在大模型报告生成并保存后才增加，不能代表每次生产。当前
仪表盘改为按外部数据中的批次顺序累计扣分，因此每台设备都有与生产记录
相对应的曲线，最后一个点与当前设备总评分一致。`ETCH-02` 从 100 分逐步
降到 45 分，风险和变化方向都得到体现。

### 大模型在系统中的正确位置是什么？

先用确定性规则生成事实数据，再把异常记录和检索到的规范交给大模型组织
分析建议。不能让大模型自行编造评分、批次或设备状态。

## 10. RAG 阶段的衔接点

进入 RAG 时优先复用：

- `build_equipment_analysis()` 提供的结构化事实；
- `anomaly_analysis.py` 的阈值和异常事件；
- `health_score.py` 和 `trend_analysis.py` 的确定性结果；
- `llm_report_generator.py` 现有的知识检索入口。

RAG 需要新增的是文档切分、向量化、检索评估和引用约束，不需要重做当前
数据管线和仪表盘。
